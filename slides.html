IoC & Dependency Injection

Das Herzstück von Spring

Das Problem ohne Spring

❌ Harte Kopplung

public class OrderService {
  // Direkte Instanziierung!
  private PaymentService pay
    = new PaymentService();

  public void placeOrder() {
    pay.charge(100);
  }
}

✅ Mit DI (lose Kopplung)

public class OrderService {
  // Abhängigkeit von außen!
  private final PaymentService pay;

  public OrderService(PaymentService p){
    this.pay = p;
  }

  public void placeOrder() {
    pay.charge(100);
  }
}
Harte Kopplung = schwer zu testen, schwer auszutauschen, schwer zu warten

Inversion of Control (IoC)

Wer erstellt die Objekte?

Ohne Spring

Dein Code entscheidet, wann und wie Objekte erstellt werden

new OrderService(new PaymentService())

Mit Spring (IoC)

Spring übernimmt die Kontrolle — du sagst nur was du brauchst

@Autowired OrderService service
Deine Klasse
braucht etwas
→
Spring Container
erstellt & verwaltet
→
Bean
wird injiziert
IoC = "Don't call us, we'll call you" — der Container steuert den Fluss

Drei Arten von Dependency Injection

// 1️⃣ Konstruktor-Injection (EMPFOHLEN)
@Service
public class OrderService {
    private final PaymentService paymentService;

    @Autowired  // ab Spring 4.3 bei einem Konstruktor optional
    public OrderService(PaymentService paymentService) {
        this.paymentService = paymentService;
    }
}

// 2️⃣ Setter-Injection
@Service
public class OrderService {
    private PaymentService paymentService;

    @Autowired
    public void setPaymentService(PaymentService svc) {
        this.paymentService = svc;
    }
}

// 3️⃣ Field-Injection (NICHT empfohlen in Produktion)
@Service
public class OrderService {
    @Autowired
    private PaymentService paymentService;  // schwer zu testen!
}
Konstruktor-Injection macht Abhängigkeiten explizit und ermöglicht final-Felder

Spring Bean-Lifecycle

1 Spring liest Konfiguration (XML / Annotation / Java-Config)
2 Bean-Definitionen werden im BeanFactory-Register gespeichert
3 new BeanClass() wird aufgerufen (Instanziierung)
4 Properties werden gesetzt (Setter-Injection)
5 Awareness-Interfaces werden aufgerufen (setBeanName() etc.)
6 @PostConstruct / afterPropertiesSet() wird ausgeführt
7 ✅ Bean ist bereit — liegt im Container
8 Bei Shutdown: @PreDestroy / destroy()

XML vs. Java-Konfiguration

Zwei Wege — ein Ziel

XML-Konfiguration Klassisch

<?xml version="1.0" encoding="UTF-8"?>
<beans xmlns="http://www.springframework.org/schema/beans"
       xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
       xsi:schemaLocation="...">

    <!-- Bean definieren -->
    <bean id="myBean" class="com.example.MyBean">
        <property name="name" value="Mein erster Bean"/>
    </bean>

    <!-- Referenz auf andere Bean -->
    <bean id="orderService" class="com.example.OrderService">
        <constructor-arg ref="paymentService"/>
    </bean>

    <bean id="paymentService" class="com.example.PaymentService"/>

</beans>

Vorteile

Konfiguration von Code getrennt
Kein Rebuild bei Änderungen

Nachteile

Verbose, fehleranfällig
Kein Compile-Zeit-Check

Java-Konfiguration Modern

@Configuration          // Diese Klasse liefert Bean-Definitionen
public class AppConfig {

    @Bean               // Methode erstellt eine Bean
    public OrderService orderService() {
        return new OrderService(paymentService());
    }

    @Bean
    public PaymentService paymentService() {
        return new PaymentService();
    }
}

// Starten:
ApplicationContext ctx =
    new AnnotationConfigApplicationContext(AppConfig.class);

OrderService svc = ctx.getBean(OrderService.class);
Java-Config ist typsicher — Fehler fallen beim Kompilieren auf, nicht erst zur Laufzeit

Observer-Pattern mit dem Spring Event-Bus

Warum Events?

❌ Enge Kopplung

// Alle anderen reagieren selbst
Publisher
kennt niemanden
→

→

→

Events implementieren

// 1. Event-Klasse
public class OrderPlacedEvent extends ApplicationEvent {
    private final Order order;
    public OrderPlacedEvent(Object source, Order order) {
        super(source);
        this.order = order;
    }
    public Order getOrder() { return order; }
}

// 2. Publisher
@Service
public class OrderService {
    @Autowired
    private ApplicationEventPublisher publisher;

    public void placeOrder(Order order) {
        // Business-Logik...
        publisher.publishEvent(new OrderPlacedEvent(this, order));
    }
}

// 3. Handler
@Component
public class EmailHandler implements ApplicationListener<OrderPlacedEvent> {
    @Override
    public void onApplicationEvent(OrderPlacedEvent event) {
        System.out.println("E-Mail senden für: " + event.getOrder().getId());
    }
}

Spring AOP

Querschnittsbelange sauber trennen

Was sind Querschnittsbelange?

📝 Logging

Methoden-Aufrufe loggen, ohne Logging-Code im Business-Code

🔒 Security

Berechtigungen prüfen, bevor Methoden ausgeführt werden

💾 Transaktionen

DB-Transaktionen automatisch starten & abschließen

⏱ Performance

Ausführungszeit messen ohne den Service-Code zu verändern

🔄 Caching

Ergebnisse zwischenspeichern, transparent für den Aufrufer

AOP-Terminologie

BegriffBedeutungBeispiel
AspectKlasse mit QuerschnittscodeLoggingAspect
AdviceWann ausführen?@Before, @After, @Around
PointcutWelche Methoden?execution(* get*())
Join PointKonkreter AufrufAufruf von getEmployee()
WeavingEinfügen des CodesSpring Proxy-Mechanismus

Wie Spring AOP funktioniert

Aufrufer
→
Spring Proxy
(AOP-Wrapper)
→
Original-Methode
// Ohne @Around: Spring injiziert Code um die Methode herum
// Dein Code sieht das NICHT — Spring generiert einen Proxy

@Aspect
@Component
public class TimingAspect {

    @Around("execution(* com.example.service.*.*(..))")
    public Object measure(ProceedingJoinPoint pjp) throws Throwable {
        long start = System.currentTimeMillis();

        Object result = pjp.proceed();   // ← Original-Methode ausführen

        long time = System.currentTimeMillis() - start;
        System.out.printf("[%s] %dms%n",
            pjp.getSignature().getName(), time);
        return result;
    }
}
Spring erstellt einen Proxy um deine Bean — du rufst immer den Proxy auf

Advice-Typen im Überblick

@Aspect
@Component
public class ExampleAspect {

    // VOR der Methode
    @Before("execution(* com.example.*.*(..))")
    public void before(JoinPoint jp) {
        System.out.println("BEFORE: " + jp.getSignature());
    }

    // NACH der Methode (immer, auch bei Fehler)
    @After("execution(* com.example.*.*(..))")
    public void after(JoinPoint jp) { ... }

    // NUR wenn kein Fehler
    @AfterReturning(pointcut = "...", returning = "result")
    public void afterReturning(Object result) { ... }

    // NUR bei Fehler
    @AfterThrowing(pointcut = "...", throwing = "ex")
    public void afterThrowing(Exception ex) { ... }

    // RUND UM die Methode (mächtigster Typ)
    @Around("execution(* com.example.*.*(..))")
    public Object around(ProceedingJoinPoint pjp) throws Throwable {
        // vor der Methode
        Object result = pjp.proceed();  // Methode ausführen!
        // nach der Methode
        return result;
    }
}

Spring Boot

Von Konfiguration zu Convention

Spring Boot: Was ist anders?

Spring Core (klassisch)

  • Explizite Konfiguration für alles
  • Web-Server separat konfigurieren
  • Dependency-Konflikte selbst lösen
  • Viele XML-Dateien

Spring Boot Convention over Config

  • Auto-Konfiguration basierend auf Classpath
  • Eingebetteter Tomcat/Jetty
  • Starter-POMs lösen Kompatibilität
  • Ein JAR, alles drin
// Das ist eine vollständige Spring Boot App:
@SpringBootApplication
public class Application {
    public static void main(String[] args) {
        SpringApplication.run(Application.class, args);
    }
}
@SpringBootApplication = @Configuration + @EnableAutoConfiguration + @ComponentScan

REST-Controller Pattern

@RestController
@RequestMapping("/api/v1/orders")
public class OrderController {

    private final OrderService orderService;

    // Konstruktor-Injection (kein @Autowired nötig bei einem Konstruktor)
    public OrderController(OrderService orderService) {
        this.orderService = orderService;
    }

    @GetMapping                              // GET /api/v1/orders
    public List<Order> getAll() {
        return orderService.findAll();
    }

    @GetMapping("/{id}")                     // GET /api/v1/orders/42
    public ResponseEntity<Order> getById(@PathVariable Long id) {
        return orderService.findById(id)
            .map(ResponseEntity::ok)
            .orElse(ResponseEntity.notFound().build());
    }

    @PostMapping                             // POST /api/v1/orders
    @ResponseStatus(HttpStatus.CREATED)
    public Order create(@RequestBody @Valid OrderRequest req) {
        return orderService.create(req);
    }

    @DeleteMapping("/{id}")                  // DELETE /api/v1/orders/42
    @ResponseStatus(HttpStatus.NO_CONTENT)
    public void delete(@PathVariable Long id) {
        orderService.delete(id);
    }
}

Docker & Container

Grundlage für jedes Cloud-Deployment

Warum Container?

❌ Ohne Container

  • "Bei mir läuft es!" — auf dem Server nicht
  • Java-Version auf Server falsch
  • OS-Unterschiede machen Probleme
  • Skalierung erfordert VM-Setup

✅ Mit Container

  • App + Laufzeitumgebung verpackt
  • Überall gleich: lokal = Produktion
  • Schnell skalierbar
  • Isolation zwischen Services

Container-Schichten:

Deine Spring Boot App (JAR)
Java 17 JRE
Alpine Linux (5MB)

Dockerfile — Best Practices

# Multi-Stage Build: Build-Stage hat JDK, Run-Stage nur JRE
FROM eclipse-temurin:17-jdk-alpine AS builder
WORKDIR /app
COPY . .
RUN ./gradlew bootJar --no-daemon

# ─── Production Stage ───────────────────────────────────
FROM eclipse-temurin:17-jre-alpine
WORKDIR /app

# Security: Non-Root-User anlegen
RUN addgroup -S appgroup && adduser -S appuser -G appgroup
USER appuser

COPY --from=builder /app/build/libs/*.jar app.jar

# Health-Check im Container (ECS nutzt dies!)
HEALTHCHECK --interval=30s --timeout=10s --retries=3 \
  CMD wget -qO- http://localhost:8080/actuator/health || exit 1

EXPOSE 8080
ENTRYPOINT ["java", \
  "-Djava.security.egd=file:/dev/./urandom", \
  "-jar", "app.jar"]
Multi-Stage: Final-Image hat kein JDK — kleiner & sicherer
Non-Root-User: Sicherheitspflicht in produktiven AWS-Deployments

AWS-Services im Überblick

🗂 ECR — Elastic Container Registry

Privates Docker-Registry in AWS. Deine Images werden hier gespeichert und von ECS gepullt.

🚢 ECS Fargate

Serverloser Container-Service. Du definierst den Container — AWS kümmert sich um die Server.

🗄 RDS

Verwaltete relationale Datenbank (PostgreSQL/MySQL). Automatische Backups, Patches, Multi-AZ.

🔐 Secrets Manager

DB-Passwörter, API-Keys sicher speichern. Automatische Rotation möglich.

⚖️ ALB

Application Load Balancer verteilt Traffic auf Container. Terminiert HTTPS. Health-Check integriert.

📊 CloudWatch

Logs, Metriken, Alarms. Zentrales Monitoring für alle AWS-Services.

ECR — Container-Image pushen

# 1. Repository anlegen
aws ecr create-repository \
  --repository-name my-spring-app \
  --region eu-central-1

# 2. Docker bei ECR anmelden
aws ecr get-login-password --region eu-central-1 \
  | docker login --username AWS --password-stdin \
    123456789.dkr.ecr.eu-central-1.amazonaws.com

# 3. Image bauen, taggen, pushen
docker build -t my-spring-app .

docker tag my-spring-app:latest \
  123456789.dkr.ecr.eu-central-1.amazonaws.com/my-spring-app:latest

docker push \
  123456789.dkr.ecr.eu-central-1.amazonaws.com/my-spring-app:latest

Sicherheit in AWS

Best Practices für produktiven Betrieb

Secrets — Niemals im Code!

⚠ NIEMALS so:

# application.properties ← im Git!
spring.datasource.password=geheim123
aws.secretKey=AKIA1234567890

# Oder so:
spring.datasource.password=\
  ${DB_PASSWORD:geheim123}
# Fallback-Wert ist sichtbar!

✅ Richtig so:

# 1. Secret in AWS speichern
aws secretsmanager create-secret \
  --name "myapp/db" \
  --secret-string \
    '{"password":"sicher123"}'

# 2. In ECS Task Definition referenzieren
# (kein Passwort im Code/Config!)
"secrets": [{
  "name": "DB_PASSWORD",
  "valueFrom": "arn:aws:...myapp/db:password::"
}]
Rule #1: Kein Secret gelangt jemals in Git. IAM Roles statt Access Keys in Containern.

Network Security — VPC & Security Groups

Internet
↓ Port 443 (HTTPS)
ALB (Public Subnet) ← SG: erlaubt 0.0.0.0/0 auf 443
↓ Port 8080
ECS Container (Private Subnet) ← SG: nur ALB darf auf 8080
↓ Port 5432
RDS PostgreSQL (Private Subnet) ← SG: nur ECS darf auf 5432
  • RDS: --no-publicly-accessible — nie direkt aus Internet erreichbar
  • Container in privaten Subnets — kein direkter Internet-Zugriff
  • Nur ALB in öffentlichem Subnet
  • Niemals Security Group 0.0.0.0/0 auf interne Services!

IAM — Least Privilege Prinzip

// ECS Task Role: Nur was die App wirklich braucht!
{
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "secretsmanager:GetSecretValue"    // Secrets lesen
      ],
      "Resource": "arn:aws:secretsmanager:...:myapp/*"
    },
    {
      "Effect": "Allow",
      "Action": [
        "logs:CreateLogStream",            // Logs schreiben
        "logs:PutLogEvents"
      ],
      "Resource": "arn:aws:logs:...:log-group:/ecs/myapp:*"
    }
  ]
}
Kein * in Actions für produktive Rollen! Jede Permission explizit vergeben.

Monitoring & Logging

CloudWatch + strukturiertes Logging

Strukturiertes Logging für CloudWatch

❌ Unstrukturiert (schwer zu durchsuchen)

log.info("Benutzer 42 hat Produkt " +
         productId + " für " + price +
         " EUR bestellt");
# CloudWatch: schwer zu filtern
2026-01-01 Benutzer 42 hat Produkt ...

✅ Strukturiert (JSON)

log.info("Order placed",
  StructuredArguments.keyValue("userId", 42),
  StructuredArguments.keyValue("productId", productId),
  StructuredArguments.keyValue("price", price));
{"level":"INFO",
 "userId":42,
 "productId":"ABC",
 "price":29.99}
JSON-Logs können in CloudWatch Logs Insights mit SQL-ähnlichen Queries durchsucht werden

CloudWatch Logs Insights

-- Alle Fehler der letzten Stunde
fields @timestamp, @message
| filter @message like /ERROR/
| sort @timestamp desc
| limit 50

-- Durchschnittliche Response-Zeit
fields @timestamp, responseTime
| stats avg(responseTime) as avgTime by bin(5m)

-- Fehlerrate pro Stunde
fields @timestamp, level
| filter level = "ERROR"
| stats count() as errorCount by bin(1h)
Alarms lassen sich direkt auf diese Queries setzen → automatische Benachrichtigung bei Problemen
